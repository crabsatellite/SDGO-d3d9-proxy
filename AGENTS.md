# Parallel development and Mod Manager integration

- Start new work from current `origin/master` in an isolated branch/worktree. Preserve other worktrees, running game services and real player/configuration data.
- Completed fixes use Git delivery: merge and push the Mod source to `master`, publish the matching client/server runtime files to their existing Git branches, and align the selected local runtime without another routine confirmation. Preserve private settings and unrelated work. Report any activation or mirror gap explicitly. Do not create ZIP/patch updates unless the user explicitly requests one.
- Client delivery must synchronize the complete authoritative gameplay runtime, including original programs, shared Mod settings, resources and the reconstructed native archive; a changed-DLL whitelist is insufficient. Use the SDGO-client repository's `maintenance/publish_runtime.py --reference "<configured owner client>"`. Keep `install.bat` and `update.bat` on the same complete synchronization path; verify the resulting runtime and quarantine retired files before reporting completion. Do not restore the retired `1_SD敢达文件恢复.exe` workflow. Personal login/settings, screenshots, logs, private credentials and recovery data remain local.
- Player downloads, helper bootstrap, updates and native archive segments prefer Codeup and automatically fall back to the matching GitHub HTTPS source when Codeup is unavailable, as explicitly requested by the user. Keep both paths on the same verified runtime and existing Git credentials; never publish credentials or require a new SSH key just to update an already working client. Continue the existing automatic Codeup mirror and read back its delivered main commit before reporting publication.
- The user has authorized routine integration, Git push and actual local deployment of completed changes without another confirmation. Finish relevant checks, preserve concurrent commits, integrate into current Mod master and push; also commit and push matching player payloads to the authoritative SDGO-client main consumed by update.bat. Rebuild affected Mods/Manager, synchronize the configured local game and framework copies, and read back installed versions/hashes and the updater client commit. Do not stop at a feature branch or ZIP, or create/refresh ZIP/release packages unless explicitly requested. Preserve authored configuration/data and other agents' preview programs; coordinate matching client/server components when needed. Read back server/database activation as applicable, report activation gaps, and never commit game originals, credentials or player data to the Mod source repository.
- Before starting or restarting native Battle hosts, read the enabled ports in `tbl_ChannelInfo` and `ServerStartUp/ServerStartUp.xml`. A folder's existence does not enable its channel; derive the launch set from the selected server's configuration rather than assume BattleServer1-7 are all enabled. Do not relax the native Unit Support Info row-count check to conceal an unregistered channel.
- All user-facing Mod configuration belongs in **SDGO Mod Manager**. Do not add another configuration EXE, HTTP server, per-Mod launcher or process-owning script.
- Player-facing gameplay actions belong in the game's relevant native page. Manager owns installation, configuration, management APIs and Mod background work; it is not the gameplay UI. Hangar sorting and duplicate exchange belong in the **unit management / 机体管理** page, without a separate desktop window, global floating toolbar or required hotkey. Preserve preview/confirmation and native server acknowledgements. If another action's in-game placement is unclear, agree on it with the user before implementing that UI.
- Every Mod must ship `manager.json`. Register readable labels, storage keys, validation and activation rules. Everyday player/server-owner operations use `audience=user`; only raw identifiers and diagnostics use `audience=developer`.
- Automatic bug fixes use `presentation=automatic_fix` and appear in the archive. Configurable starter/gameplay/server features stay in normal management.
- Register persistent background work with `workspace.services.register(id, title, controller, start)`. The Manager owns start/stop, health, retry and persisted enablement. Use `/api/services/<id>`; do not add module-specific worker lifecycle endpoints or restore old launcher ownership.
- Obtain internal IPC resources through `workspace.services.resource(id, factory)`. Manager shutdown releases them. Native in-game hooks/packet bridges remain Mod runtime code; do not move game processes into the service supervisor.
- Reuse the Manager's session, revision, path, panel and export contracts. Preserve authored workspaces and do not publish credentials, real account data or game assets.
- Keep each feature's AI configuration/debug and bug-report handoff accurate. Repair PR bodies must include actual `AI models:` names/versions (explicit Unknown if undisclosed), AI scope, human verification and remaining uncertainty.
- Commits are authored solely by the user. NEVER add `Co-Authored-By` lines.
