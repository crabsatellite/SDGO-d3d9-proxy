# 统一 Mod Manager 设计

## 产品入口

管理功能只提供 `SDGO Mod Manager.exe` 一个入口。它启动同一个本机界面和管理服务；不再为每个 Mod 提供独立 EXE、启动脚本、端口或网页。Mod 游戏运行库不依赖 Manager 常驻；确实需要后台工作的模块以内部服务登记。

玩家在游戏中使用的操作接入相关原生页面：机库整理、重复机体兑换放在「机体管理」页，保留预览、确认和服务器回执，不另开桌面窗口、不挂全局悬浮工具栏、不要求记快捷键。Manager 负责安装、配置、管理接口与 Mod 后台任务；普通玩家不应离开游戏完成这些游玩操作。其他功能若无法确定合适的游戏内位置，先与用户商量再实现界面。

首次启动默认是日常管理：普通玩家和服主都可选择客户端/服务器，添加 Mod、管理商城/副官/扭蛋机、设置奖励和联机、导入或分发配置包。管理服务器属于正常用户能力，不作为开发权限隐藏。

只有内部代号、原始字段名、Hook 符号和诊断开关放进开发信息视图。相关开发接口会检查当前模式；收起开发信息不影响日常管理能力。自动 Bug 修复不占据日常功能列表，只在修复归档查看。新账号默认内容虽然原分类属于 fixes，但它是服主日常配置，仍显示在功能列表。

每个功能提供“复制给 AI 配置/调试”和“发现 Bug，复制给 AI 报告”。说明包含原理、组件/配置位置、地址、可调点、版本和真实验收边界；报 Bug 的文本指向统一 GitHub 仓库，要求 AI 先查重复 issue，再根据真实复现创建报告。生成说明不会自动发 issue，也不读取或复制密码、令牌和原生数据库凭据。Issue 用说明不附带本机绝对路径或端点。

## Mod 注册契约

每个 Mod 附带 `manager.json`，声明版本、标题、分类、适用宿主、玩家说明、配置字段及动作。字段声明类型、默认值、范围、存储文件/节/键、可见模式和生效方式。动态内容模块通过标准 Provider 返回集合、编辑字段、动作和状态；不提供另一个 Web 服务，也不将任意脚本路径作为浏览器可执行命令。

同一个 ID 的客户端/服务端组件共享功能页，配置始终绑定一个明确宿主，不能误把客户端配置写到服务端。未认识的第三方 Mod 可以显示安装信息和自身启用开关；详细配置需要它提供注册文件，不能猜测并改写未知字段。

## 统一能力

- **配置**：表单生成、字段校验、原文件注释/编码保留、版本指纹、原子保存、只修改登记的键。区分已保存、需要重启、实际运行确认。
- **集合**：商城商品、副官、扭蛋机统一在框架内列出、搜索、新增、编辑、删除、恢复和导出。原有业务校验由 Provider 复用；删除数据与删除旧 UI 入口是两件事。
- **动作**：声明参数和结果，统一处理加载、错误、产物下载与执行进度。配置包只包含明确允许的客户端文件，不包含服务端凭据、数据库快照或管理器本机路径。
- **状态**：静态配置不冒充游戏运行成功。保留各 Mod 的真实心跳、回执及手动验收边界。
- **工作区**：选择客户端和服务端路径后保存到服主本地配置；通用源码/分发包无作者电脑路径。数据保留原路径或通过显式迁移复制后校验，不重置既有商品、副官、扭蛋机和钱包队列。

## 本轮迁移范围

包含当前 master 的全部 Mod、奖励网页、FRP 配置生成和 AI 清单工具；按用户追加授权，也迁入本机已部署的商城 EXE、副官和扭蛋机网页入口。其他分支的源码工作区保持原样，迁入的是固定版本的业务模块与注册契约。仓库已命名为 `crabsatellite/SDGO-Mod-Framework`。

迁移顺序：盘点路径和进程身份 → 构建统一 Manager → 导入现有配置并只读核对 → 通过接口/界面/打包验证 → 切换本机唯一入口 → 删除精确登记的旧 UI、启动器、桌面快捷方式和废弃 EXE。真实配置、原生游戏 EXE、Mod DLL、账号和恢复备份不属于废弃入口。

## 验证要求

检查所有随包 Mod 都有注册；日常管理能操作客户端和服务器，自动修复只进归档，开发诊断信息按视图隔离；AI 说明和 Bug 报告不泄露凭据；保存不损坏未登记键；并发更改会拒绝覆盖；跨目录、ZIP 路径和任意命令不可通过输入注入；集合 CRUD、编译/导出与已有业务输出一致；分发包可在空白目录启动，只有一个用户入口，不依赖旧 UI 文件。对游戏内效果的验收仍由用户手动完成。
