# 任务房与对战房的房名限制：调查与 Mod 方案

调查日期：2026-11-01。分支：`investigate/room-title-limit`。

**结论：当前支持的原版程序在客户端发送、服务端存储和房间信息回包中均按
20 字节处理房名。任务与对战都受影响。可以通过配套 Mod 扩展，但只改输入框或
把现有 AI Mod 的常量改大不能解决。本文保留原生限制调查和设计背景；当前实现与安装见[长房名 Mod](room-titles.zh-CN.md)，自动验证与人工验收边界见[验证记录](room-titles-verification.md)。**

## 已核对的证据

对实际 `GOnline.exe`、`BattleServer.exe` 做只读字节检查，未启动游戏、附加进程、
修改 EXE、改数据库或变更已安装 Mod。完整二进制身份及 14 个检查点见
[静态检查记录](investigations/room-title-static-audit.json)。

| 层 | 路径 | 已观察到的行为 |
| --- | --- | --- |
| 客户端 | 普通建房 `0x008D42D0` | 从 `GameRoomNameEdit` 取值，转为窄字符串，以 20 字节复制到 `0x640` 请求；发送长度固定为 `0x53`。 |
| 客户端 | 任务建房 `0x009EE1A0` | 选择任务模式 5/8，读取房名，先截到 20 字节，再构造同类 `0x640` 请求。 |
| 客户端 | 任务设置 `0x0084C300` | `CServiceCooperateRoomSetting` 的确定按钮与 Enter 路径都调用此函数；标题长度截到 20，发送 `0x9ED`、`0x3E` 字节请求。 |
| 服务端 | 大厅房间创建 `0x004FDB70` | 标题长度写入 `WaitRoom +0x53`，从请求 `+0x13` 向房间 `+0x54` 固定复制 20 字节。 |
| 服务端 | 战斗房间设置 `0x004BEC60` | 标题长度写入 `WaitRoomEx +0x79`，向 `+0x7A` 固定复制 20 字节。 |
| 服务端 | 战斗房间改名 `0x004DCA40` | 同样写入 `+0x79`，向 `+0x7A` 固定复制 20 字节。 |
| 服务端 | 房间信息构造 `0x004F60F0` | `0x004DD120` 通过跳转桩调用这里，向 `0x91F` 房间信息包固定复制 20 字节房名。 |
| 现有 Mod | `coop_ai` | 任务开始时经用户到大厅房间的映射读取 `WaitRoom +0x53/+0x54`；最多复制、解析 20 字节。 |
| 现有 Mod | `pvp_ai` | 从战斗房间 `WaitRoomEx +0x79/+0x7A` 读取标题；最多复制、解析 20 字节。 |

客户端任务设置的类型对应关系由原版 RTTI 和 vtable 核对：
`CServiceCooperateRoomSetting` vtable `0x00E9DE8C`，按钮处理
`0x00852AE0`、Enter 处理 `0x00852F30`，两者都调用 `0x0084C300`。
普通建房服务 `CServiceMakeRoomSetting` 的 vtable 为 `0x00EA3CD4`。

定位时复用了现有 `decompiled/gonline/chunk_022.c`、`chunk_025.c`、`chunk_030.c`
中的伪代码，并用当前 EXE 原始指令复核上表关键路径。历史服务端 MAP/伪代码有
跳转桩和函数边界错误，不能仅凭其旧函数名确定实际处理器。上述地址以当前二进制为准。

此外，通过 REA CLI / Ghidra 12.1.4 重新分析了当前服务端的改名函数
`0x004DCA40–0x004DCDAD`。Evidence ID：
`ev_b6e855210894cf6b277b0528c460312e57e78303c3f36815790a592651bd8c9d`。
完整记录保存在本 worktree 的 `build/investigation/room-titles/battle-rename.rea.json`，
其中可直接看到 `_strncpy(room + 0x7A, request + 8, 0x14)`；这是静态反编译观察，
不是原始源码或运行时验收。使用临时命令环境指向已有 Ghidra/JDK，没有改全局工具配置。

“20 字节”不能理解为“20 个中文字符”。实际编码还受已有语言补丁影响：
这份原版客户端调用转换函数时传入代码页 `0x36A`（874），现有 SDPlus
会改写该代码页。`coop_ai` / `pvp_ai` 注释中的 CP949 不是本次对运行时编码的确认。
ASCII 规则命令的计数不受这个区别影响。扩展字段应明确使用 UTF-8。

原生代码虽存在与 20 比较的分支，本次**不据此宣称服务端可靠拒绝一切超长请求**：
已检查的若干条件组合不能提供这种保证。固定大小的复制及报文布局本身足以说明
放宽输入框不能传递完整长标题。

## 产品行为

以 `room_metadata` 私有库共享协议和状态，安装部分为 `room_titles`、`room_titles_agent`、`room_titles_server` 三个功能 Mod，与 FRP、Sakura、具体服主地址解耦。
服主安装服务端部分；玩家由通用 Mod 包获得客户端部分，照常启动游戏。
不要求另开“开始联机”、运行脚本、安装 Python，或逐房间分发配置。

- 任务房和对战房都能创建、修改长标题，建议默认上限为 128 个 Unicode 标量，
  同时限制 UTF-8 数据不超过 512 字节；这是扩展协议的产品上限。
- 房间列表、房内标题和改名框都使用同一份服务端确认过的完整名称。
  窄列表按可用宽度省略，并提供悬停或详情查看全文；房内可以换行显示。
- 保留现在房名里写规则的用法。`!ai`、队伍数量、等级等命令可以在第 20 字节之后，
  仍由任务与对战对应的服务端 Mod 读取、执行。
- 提交失败时显示失败并保留可编辑文本，不静默截掉规则。点击开始前，应已收到
  服务端的标题/规则修订确认，避免界面新名称、实际旧规则。
- 房名中的文字说明仍是说明；只有已有规则解析器支持的命令才自动生效。

## 为什么需要扩展元数据

保留原生结构和旧报文中的短标题字段；完整标题由 Mod 单独存储、同步。
例如玩家输入长标题时，原生字段仍是编码后不超过 20 字节、不会截断编码字符的
短名称。扩展字段保存完整 UTF-8 标题。不能把 128 字节直接写入原来的 20 字节区域，
否则会覆盖相邻房间字段；也不能擅自增长旧数据包并期待原版处理器自动兼容。

原生兼容字段不应再作为扩展房间的规则来源，因为它可能只有标题开头。
服务端为每个房间维护“完整标题及修订号”；两种 AI Mod 通过统一的版本化查询接口
取得有效标题，再沿用各自的命令语义。未使用扩展的房间继续读原生短标题。
查询接口属于功能 Mod，公共 core 不存储房间规则。

任务路径需要将大厅 `WaitRoom` 与启动时的战斗实例正确关联；对战路径需要覆盖
`WaitRoomEx`。不能只以房主用户 ID 或房间内存地址作为长期键：房主会变、地址和
房间编号会复用。键至少包含服务实例、房间 ID 和本次创建的 generation，销毁即清理。
任务验收还须分别覆盖现有 `coop_ai` 支持的模式 5/8/10；上表客户端具体追踪到的是
模式 5/8 的建房及任务设置路径，模式 10 的自动建房、共用标题栏和 subtype 2 改名路径也已在实现阶段追踪，见[原生 UI 证据](investigations/room-title-native-ui.md)。

## 同步与兼容要求

1. 客户端与服务器先确认支持的扩展协议版本及长度上限。未经确认不向旧处理器发
   新报文，旧客户端仍只接收原版布局。
2. 优先复用已认证的游戏连接。先追踪 Agent/World/Battle 的完整转发与分发表，再决定
   哪些进程需要扩展处理器；尚未证明未知 opcode 能穿过原生中间层。
   不在这里预留某个未经冲突审查的 opcode，也不新增隐含的 HTTP 服务、固定公网地址
   或 Sakura 隧道需求。
3. 房间创建 ACK 后才能把完整名称绑定到服务端生成的房间身份；随后提交标题修订，
   服务端确认后更新房主界面、列表和已入房玩家。新进房、重连、刷新列表都须取得快照。
4. 服务端核验当前连接确为该房间房主，校验 UTF-8、长度和控制字符；拒绝旧 generation、
   过期修订、跨房间修改。房主转移保留房间标题但更新修改权限。
5. 对需要长规则的房间，应要求参加者具有兼容客户端 Mod。未装 Mod 的客户端只能看到
   短名称，不能把它当作完整规则视图。服主可选拒绝其加入此类房间，且需明确提示原因。
6. 客户端不能单方面宣称服务器已支持长标题。服务器无扩展时，明确显示原生限制并在
   提交前拦截超长输入；不要偷偷丢弃尾部。扩展安装、升级保留服主配置，不改无关 Mod。

## 实施顺序与验收

本功能没有向运行环境安装补丁。实施与验收分为：

1. 钉定建房、任务设置、对战设置、改名、列表、入房、离房和销毁的 Hook 与完整路由。
2. 实现服务端元数据、能力协商和快照/修订同步，验证旧客户端报文布局不变。
3. 实现两个模式的输入与显示，再改接 `coop_ai`、`pvp_ai` 的完整标题查询，
   移除仅对扩展标题不适用的 20 字节解析上限。
4. 自动测试：20/21 字节边界，UTF-8 多字节字符，规则位于第 20 字节之后，
   多房间隔离，房间编号复用，房主转移，乱序修订，重连、无权限修改、协议不兼容。
5. 人工验收：任务房和对战房各自建房、改名、重新入房；第二个客户端查看相同全文；
   开始任务/对战后核对规则实际生效。此项继续按用户要求由用户手动完成。

初始调查阶段完成了原生限制和静态检查；实现与验证记录另列在功能指南。
真人任务/对战和双客户端显示一致性继续由用户手动验收。

## 重跑静态检查

`tools/audit_room_title_limits.py` 只用 Python 标准库，输入均由调用者指定：

```powershell
python tools/audit_room_title_limits.py --client D:\SDGO\GOnline.exe --battle D:\Server\BattleServer.exe --out title-audit.json
```

它先验证完整 SHA-256，再经 PE section table 把 VA 映射到文件偏移，比对 14 个锚点。
不支持的二进制返回失败，不猜测新地址；输出文件已存在时拒绝覆盖。
这些检查验证具体文件中的静态证据，不等于扩展 Mod 的运行测试。
本轮 14 个锚点均匹配；另检查了不支持的二进制、无效 PE 和未映射地址的拒绝行为。
