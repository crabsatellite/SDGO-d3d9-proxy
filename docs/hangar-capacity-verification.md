# 机库容量验证范围

本功能在独立分支 `investigate/hangar-capacity` 开发，以 `e6364a7` 为基线。
第一版自动保障原生 1200 格，不实现超过 1200 格或会话中的动态增长。

## 自动检查

Win32 Release 使用仓库严格编译选项和静态 CRT。策略夹具通过 57 项检查；
包含实际产品包装器的原生夹具通过 107 项检查。共享 WorldServer 符号文件
15 个符号全部匹配，零拒绝。原生 ABI 与客户端边界见
[原生证据](investigations/hangar-capacity-native.md)。

2026-11-01 的完整离线回归首次为 38/45 通过，其余 7 项为进程超时；原设置下重跑通过
其中 5 项。分类开关在独立生成的 CTest 副本中将等待上限从 60 秒放宽到 300 秒后通过。
AI 目录集成同样在 300 秒处超时，已输出通过的 12 个客户端场景和 2 个服务端场景；
其余 10 个服务端场景使用同一脚本的限定循环副本全部通过，编译产物与断言未改动。
因此原有测试范围的断言均有通过证据，但**整套单次 CTest 并未全绿**。
产品及源测试的超时设置均未为此修改。

隔离 SQL 全套 **11/11 组通过**，包含同账号/不同账号并发、锁竞争与重试，
实际 core + Mod DLL 的启用/禁用两条路径，以及提供者命令超时后的会话恢复。
临时凭据文件及本次拥有的容器均已清理。
[哈希回执](investigations/hangar-capacity-verification.json)绑定了产品源码、测试源码和最终 DLL。

可重跑的构建与离线检查：

```powershell
cmake -S . -B build -A Win32
cmake --build build --config Release --parallel 3
ctest --test-dir build -C Release --output-on-failure
```

SQL 检查命令见[使用说明](hangar-capacity.zh-CN.md)。它使用新建、带所有权标签的
隔离 SQL 容器和临时随机凭据，不读取真实服务端配置或连接现有游戏库。

| 范围 | 检查内容 |
|---|---|
| 策略 | 基础 24 + 额外 1176；只增不减；非法账号/容量/库名拒绝；Unicode 库名转义 |
| 原生包装 | 原对象、连接和参数身份；先保障再调用原函数一次；原函数错误透传；失败不提前发布容量；LastError |
| 数据库 | 新旧账号、较大已有容量、幂等、补洞、区间外编号保留、结构/过程不匹配拒绝 |
| 实际 DLL | 真实 core 与 Mod DLL、真实 SQLOLEDB、启用与禁用、原生命令/绑定保留 |
| 事务 | COM 延迟事务和 SQL 调用方事务保留；写入错误回滚；命令超时后的会话恢复和重试 |
| 数据保护 | 不批量更新其他账号；机体数量、64 位序号、涂装与货币保持不变 |
| 分发 | 完整包、指定功能包、模拟 World 安装；默认关闭；更新保留服主开关与超时配置 |

## 真人验收（尚未执行）

自动检查不代表真实客户端画面、领取流程或联机已通过。按用户要求，真人游戏验收手动进行：

1. 在隔离测试服的已停止 WorldServer 安装并启用 Mod，再正常启动；检查加载日志。
2. 分别用原有账号和新账号正常登录，查看 1200 格、34 页和末页 12 格；核对已有机体、涂装和出击配置。
3. 在测试数据中验证 1099、1100、1200 号槽的显示与实际领取，检查商店、礼物、合成/恢复等实际使用的来源。
4. 保存、退出并重新登录，核对新增机体及槽号保留，货币和规则符合原生领取行为。
5. 在已有更大容量的测试账号上核对原值未被缩小；本版本不宣称其超过 1200 的界面兼容性。
6. 停服关闭 Mod 后再登录，确认已增加容量与所得机体保留；关闭只停止后续保障调用。

当前实现未部署到真实数据库或运行中的服务器，未启动游戏，未进行自动真人验收。
